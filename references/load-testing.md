# 压力测试方法（v4.2 新增）

模板里已要求"压测场景 + 通过标准"。本文件补充**怎么测才测得准**——很多压测测出来的是压测机的网络，而不是服务器。

---

## 一、先问清用户从什么网络来

峰值估算之外，还要问：**用户是从哪里访问的？**

- 学校/企业 WiFi、机房：几百人共用一个或几个公网出口 IP
- 手机 4G/5G：运营商级 NAT，同一基站附近的大量用户也可能共用出口 IP
- 家庭宽带：基本是独立 IP

**影响**：所有"按 IP 限流"的规则（登录频率、接口频率、失败次数封禁）都必须按**共用出口的最坏情况**设定。防暴力破解应主要依赖"按账号锁定"，而不是按 IP。

> 案例：某校园系统最初登录限流为"同一 IP 每分钟 5 次"。一个班在教室连 WiFi 同时登录，第 6 个人起全部被拒。按 IP 的失败计数封禁阈值最初设为 100 次/10 分钟，几百名学生首次登录输错初始密码就足以触发——会误封全校。

## 二、压测场景要按真实节奏

不要只压单个接口，要模拟**一个真实用户完整走一遍**，带上思考时间：

```
同时点登录 → 首次改密（输入新密码要 5–15 秒）→ 逐题作答（每题 2–4 秒，前端每次答完自动保存）
→ 提交 → 部分人进入 AI 环节（真实调用第三方 AI，看排队）→ 异步任务完成 → 查看结果
```

- 最坏情况：所有人在**同一秒**点登录（老师说"开始"）
- 页面加载会同时发出多个请求（用户信息、进度、配置……），要一起模拟
- AI/第三方环节：按真实比例抽一部分用户调用真实服务，评估排队时间和费用

## 三、在哪里压

- **压测机的带宽和延迟会成为瓶颈**：本地网络慢时，500 个虚拟用户测到的是本地网络
- 推荐：在服务器本机（或同机房另一台机器）运行压测脚本，访问本机的 Nginx 入口；这样同时也模拟了"所有用户同一个出口 IP"
- 压测脚本以后台方式运行（如 `docker run -d`），SSH 断开不影响；结果写文件，事后取回
- 同时采样服务器资源：每 5 秒记录各容器 CPU/内存，结束后检查 OOM、容器重启、后端错误日志

## 四、通过标准（示例，按项目调整）

| 指标 | 标准 |
|---|---|
| 登录（含首次改密）| 500 人同时登录，全部成功，最后一人 ≤ 15 秒 |
| 普通接口 | p95 ≤ 1 秒，5xx = 0，429（限流）= 0 |
| 写入接口（保存进度/提交）| p95 ≤ 1 秒，无数据丢失 |
| 异步 AI 任务 | 排队最长等待 ≤ N 分钟，且前端有排队提示 |
| 服务器 | 内存峰值 < 80%，无 OOM，无容器重启 |

## 五、常见瓶颈（压测前先自查代码）

- 每个请求都新建 Redis/数据库连接，而不是用连接池
- 中间件里每个请求都查一次很少变化的数据（租户/学校/配置）而没有缓存
- 高频写接口里做了不必要的校验查询
- 密码哈希（bcrypt）在事件循环里同步执行，或持有数据库连接时做哈希
- Nginx 默认 `worker_connections 1024`、未开 HTTP/2（每个浏览器开多条连接）
- 等待第三方 AI 回复期间一直占着数据库连接

## 六、压测数据隔离

在生产环境压测时，建一个独立的"压测租户"（如压测学校），账号和数据都在里面，测完停用——避免污染真实业务数据和研究数据。压测要避开真实用户使用时段。
